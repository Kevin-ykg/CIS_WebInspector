# 开发调试与验证

返回 [交接入口](README.md)。命令均从项目根目录执行；路径含空格时使用引号。

## 1. 构建的唯一源头

- 应用：[CIS_WebInspector.csproj](../CIS_WebInspector.csproj)，.NET Framework 4.8 / WPF / x64。
- 原生：[Native/CMakeLists.txt](../Native/CMakeLists.txt)，C++17 / OpenCV + contrib 4.10.0 / IPP。
- 准备 VS 的 .NET 桌面及 C++ 桌面工作负载、.NET 4.8 开发目标包、CMake；部署需要对应 VC++ x64 运行库。
- Volans 引用及原生 DLL 从工程指定的相对位置复制；TLC DLL/CameraLink 驱动由设备环境提供。本轮不修改厂商 SDK。

```powershell
powershell -ExecutionPolicy Bypass -File Tools/Build-VisionNative.ps1 -Configuration Release
dotnet restore CIS_WebInspector.sln
dotnet build CIS_WebInspector.sln --no-restore -c Debug -p:Platform=x64
dotnet build CIS_WebInspector.sln --no-restore -c Release -p:Platform=x64
```

首次原生构建下载固定版本 OpenCV 并校验归档，时间/空间开销较大。之后只改自有 C++ 时可复用缓存：

```powershell
cmake --build obj/VisionNative/core-build --config Release --parallel 2 -- /p:UseStructuredOutput=false
dotnet build CIS_WebInspector.sln --no-restore -c Debug -p:Platform=x64
```

第二步会复制新 DLL。只保存 cpp 或只构建 C#，不会自动重编 C++。不要修改生成的 vcxproj；新增文件必须进入 CMake。删除 obj 可以重建，但其中测试输出/尚未导出的基线不能再凭代码还原。

## 2. 断点应该打在哪里

| 问题 | 第一组断点 | 下一组 |
|---|---|---|
| 帧没有进入检测 | MainViewModel.Acquisition 的 OnFrameReady / ProcessQueuedFrame | ImageStitcher.ProcessOwnedFrame |
| 二维码不识别 | QrCodeDetector.Detect | CisQrAdapter::detect → QrDetector::detect → 对应策略函数 |
| 拼接后没有产品结果 | InspectionJobRunner.Run 的提前返回 | Reporting 的状态原因；配置/排版/Alpha |
| 大图对不齐 | ImageAligner.ComputeTransform | alignment_global.cpp / alignment_marks.cpp |
| 零件对不齐或误检 | PatchCropper ROI；PatchDefectDetector.Detect | patch_detector.cpp::detect → patch_alignment.cpp::register_patch / patch_fine_line.cpp::fine_line |
| 全局图标记不对 | PatchCropper.Preview.cs | GlobalRoi、OriginalRect、显示比例 |

### 在 patch_detector.cpp 的 detect 中打断点

推荐使用 **原生 Debug + 独立应用输出目录 + Visual Studio 附加到进程**。下面从构建到命中断点完整走一遍，不需要改算法，也不需要把 C++ 项目加入 WPF 解决方案。

`CIS_WebInspector.sln` 只构建 C# 应用，**不会自动编译 C++**；`CIS_WebInspector.csproj` 的 `VisionNativeConfiguration` 默认是 `Release`，即使工具栏选择 `Debug | x64` 也一样。只按 F5、只保存 cpp 或只编译 C#，不能保证正在运行的是可调试的 C++。

#### 第一步：确认构建环境和当前产物

在 Visual Studio Installer 中确认安装“.NET 桌面开发”“使用 C++ 的桌面开发”、.NET Framework 4.8 目标包、MSVC x64 工具和原生工程要求的 Windows SDK；另需 PATH 中可用的 CMake、dotnet。不要只检查是否安装了 VS。

**2026-10-28 本次核查：**`obj/VisionNative` 已重新出现，含 OpenCV/contrib 源码、OpenCV 构建缓存、原生生成工程和 Release DLL；原生 `Debug/CISVisionCore.dll`、`Debug/CISVisionCore.pdb` 仍缺失。实际执行 Release 增量构建报 `MSB8036`（找不到 Windows SDK `10.0.26100.0`）。已有 DLL 不等于当前环境可以重新编译，源码准备成功也不等于完整恢复成功。执行证据见 [维护记录](维护记录.md#2026-10-28原生-detect-断点交接与实际构建核查)。

遇到同一错误，先在 VS Installer“单个组件”中安装所要求的 Windows SDK，再重跑下面的构建。若团队确需换 SDK，应通过 CMake 配置并重新生成两个构建树、重新验证；不要直接编辑 `obj` 下的 vcxproj。当前要求可只读查看：

```powershell
Select-String -LiteralPath 'obj/VisionNative/core-build/CISVisionCore.vcxproj' -Pattern 'WindowsTargetPlatformVersion'
```

#### 第二步：生成原生 Debug DLL 和 PDB

若编译 OpenCV 时出现 `cfloat(10,10): fatal error C1083`、无法找到 `float.h`，先修复 Windows SDK/UCRT 开发文件。MSVC 的 `cfloat` 已找到，但它依赖的 C 运行库头文件未找到；最后的“CMake 失败，退出码 1”只是脚本汇总。打开 Visual Studio Installer → Community → 修改 → 单个组件，安装/修复工程要求的 Windows SDK（本次为 `10.0.26100.0`），确保包含 UCRT 头文件和 x64 库。仅安装 VC++ 可再发行运行库不能补齐开发头文件。安装后关闭旧终端，重新打开开发终端，从项目根目录重跑本节命令，无需先删除 OpenCV 缓存。

默认安装路径可这样检查；自定义安装应换成实际 SDK 根目录：

```powershell
Test-Path 'C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\ucrt\float.h'
Test-Path 'C:\Program Files (x86)\Windows Kits\10\Lib\10.0.26100.0\ucrt\x64\ucrt.lib'
```

两项应为 True。若文件存在仍报错，再核对生成工程选用的 SDK 版本、MSBuild 的 `UniversalCRTSdkDir` / `UCRTVersion` 和实际包含路径，不要手工下载单个 float.h、修改 cfloat 或给各 OpenCV 工程硬填 include 路径。UCRT 开发文件归属见 [微软 UCRT 说明](https://learn.microsoft.com/en-us/cpp/porting/upgrade-your-code-to-the-universal-crt)。

先关闭占用本次调试输出的程序、停止调试。在项目根目录执行，每一步成功后再进行下一步：

```powershell
powershell -ExecutionPolicy Bypass -File Tools/Build-VisionNative.ps1 -Configuration Debug
if ($LASTEXITCODE -ne 0) { throw '原生 Debug 构建失败，先处理上方错误' }
Get-Item -LiteralPath 'obj/VisionNative/core-build/Debug/CISVisionCore.dll', 'obj/VisionNative/core-build/Debug/CISVisionCore.pdb'
```

第一次 Debug 会编译对应配置的 OpenCV 静态依赖，可能耗时较长；已有 Release 库不能替代 Debug 库。脚本保留 OpenCV/contrib 4.10.0、IPP 和现行参数，不为调试改变阈值或关闭算法组件。生成的自有核心 Debug 工程为禁用 C++ 优化、输出调试信息。

**只有完整 Debug 构建已成功**，后续仅改自有 cpp 时才可用增量命令：

```powershell
cmake --build obj/VisionNative/core-build --config Debug --target CISVisionCore --parallel 2 -- /p:UseStructuredOutput=false
if ($LASTEXITCODE -ne 0) { throw '原生 Debug 增量构建失败' }
```

#### 第三步：构建使用原生 Debug 的应用，复制匹配符号

以下使用独立目录，保留 `bin/x64/{Debug,Release}/net48` 的程序、配置及 DLL。所有命令在同一个 PowerShell 窗口执行；`$debugApp` 是绝对路径。

```powershell
$debugApp = Join-Path (Get-Location).Path 'obj/NativeDebugApp/Debug/'
dotnet restore CIS_WebInspector.sln
if ($LASTEXITCODE -ne 0) { throw '托管依赖恢复失败' }
dotnet build CIS_WebInspector.sln --no-restore -c Debug -p:Platform=x64 -p:VisionNativeConfiguration=Debug "-p:OutputPath=$debugApp"
if ($LASTEXITCODE -ne 0) { throw '应用 Debug 构建失败' }
Copy-Item -LiteralPath 'obj/VisionNative/core-build/Debug/CISVisionCore.pdb' -Destination $debugApp

$nativeHash = (Get-FileHash -LiteralPath 'obj/VisionNative/core-build/Debug/CISVisionCore.dll' -Algorithm SHA256).Hash
$appHash = (Get-FileHash -LiteralPath (Join-Path $debugApp 'CISVisionCore.dll') -Algorithm SHA256).Hash
if ($nativeHash -ne $appHash) { throw '应用 DLL 与本次原生 Debug DLL 不一致' }
```

项目后置构建自动复制 DLL，**不复制原生 PDB**。每次重新链接 C++ 后，重新构建应用并复制该次 PDB；旧 PDB 不能用于新 DLL，文件同名也不代表匹配。也可在 VS“工具 → 选项 → 调试 → 符号”中加入 `core-build/Debug` 的绝对目录，但仍需在模块窗口确认实际加载成功。

独立输出默认没有现场 `app_config.json`。首次可从现有 Debug 运行目录复制一份，目标已存在时不覆盖：

```powershell
$debugConfig = Join-Path $debugApp 'app_config.json'
if (-not (Test-Path -LiteralPath $debugConfig)) {
    Copy-Item -LiteralPath 'bin/x64/Debug/net48/app_config.json' -Destination $debugConfig
}
```

源配置不存在时，通过调试程序“参数设置”配置实际路径。核对副本的 `DebugLogPath`、`TiffImageDir`、`CroppedOutputDir`；保存图片时使用专用调试输出目录。逐零件调试可在**调试副本**中临时设置 `DefectMaxParallelism=1`，保存后重启程序；这只限制零件 worker，不关闭采集、UI、保存或 OpenCV 内部线程。不改变现场阈值及算法开关。

#### 第四步：打开源码、启动程序并附加调试器

1. 用 Visual Studio 打开根目录 `CIS_WebInspector.sln`，通过“文件 → 打开 → 文件”打开仓库的 `Native/src/patch_detector.cpp`。定位 `namespace cis::patch` 中的 `PatchResult detect(...)`，在函数内第一条可执行语句 `auto started = Clock::now();` 上按 **F9**。当前核查为第 132 行，后续以函数和语句为准，不在签名、注释或大括号处定位。
2. 可在 `Services/PatchDefectDetector.cs` 调用 `PatchNativeInterop.cis_patch_detect(...)` 的语句、`Native/src/patch_api.cpp` 的 `cis_patch_detect` 函数内同时打断点，便于逐层确认。
3. 双击 `obj/NativeDebugApp/Debug/CIS_WebInspector.exe` 启动，先不要开始采集。也可在刚才的 PowerShell 窗口执行 `Start-Process -FilePath (Join-Path $debugApp 'CIS_WebInspector.exe') -WorkingDirectory $debugApp`。
4. VS 选择“调试 → 附加到进程”（**Ctrl+Alt+P**），找到此 `CIS_WebInspector.exe`；多个同名进程时按路径/PID 核对。代码类型点击“选择”，同时选中 **本机 / Native** 和 **托管（.NET Framework 4.x）/ Managed (.NET Framework)**，再附加。本项目是 net48，不选 .NET Core 类型。
5. 只调 C++ 时附加“本机”也可命中，同时观察 C# 和跨语言调用链则需两种引擎。DLL 尚未加载时断点可以暂时为空心，开始回放后再检查。

直接打开 cpp 足以打断点；需要完整 C++ 包含路径和跳转索引时，可另开一个 VS 窗口打开 `obj/VisionNative/core-build/CISVisionCore.slnx`（当前 CMake/VS 2026 的实际产物；其他生成器可能为 `.sln`），查看 `CISVisionCore` 的源文件。继续由附加应用进程的窗口负责本次调试，DLL 工程本身不是可直接启动的 WPF 程序。不要另建一套默认 CMake 构建目录后误以为应用会自动加载它。

若习惯 **F5 从 C# 启动**：在 C# 项目属性“调试 → 调试器引擎”启用“本机代码调试”（不同 VS 版本也可能位于调试启动配置界面）。还必须保证该次 VS 构建也传入 `VisionNativeConfiguration=Debug`、复制同次 PDB，并检查启动目录。命令行的 `-p:` 参数只对当次构建生效，**不保存为 VS 后续构建设置**；普通 F5 构建仍可能把 DLL 换回 Release。本节附加流程直接启动指定 EXE，可避免这个配置歧义。

#### 第五步：触发零件检测并核对模块

1. 在调试程序中点击“离线加载”，选择已知可用的**原始帧图库**，再点击“开始采集”。不能用一张零件结果 JPEG 代替原始帧序列；序列需能完成相邻二维码拼接，结束二维码能关联排版日志、带 Alpha 的 TIFF/PNG 和非 QRCode 的有效零件 ROI。
2. 调用链应为：`InspectionJobRunner.Run → PatchCropper.CropAndSave → PatchDefectDetector.Detect → PatchNativeInterop.cis_patch_detect → patch_api.cpp::cis_patch_detect → cis::patch::detect`。白墨阶段先执行，第一次进入原生 DLL 不一定已经到达零件检测。
3. 运行后需查看模块时，在 VS“调试 → 全部中断”，再打开“调试 → 窗口 → 模块”（**Ctrl+Alt+U**），搜索 `CISVisionCore.dll`。确认**路径**是 `obj/NativeDebugApp/Debug/CISVisionCore.dll`、**符号状态**为已加载；必要时右键“加载符号”，选择同次 `CISVisionCore.pdb`。“符号加载信息”可查看查找/拒绝原因。确认后按 F5 继续。
4. 进入 `detect` 时，断点应为实心，黄色箭头停在语句上。用 **F10** 逐过程、**F11** 进入自有函数、**Shift+F11** 跳出、**F5** 继续；不必逐步进入每个 OpenCV 算子。

只观察某一零件时，在 C# `PatchDefectDetector.Detect` 调用 P/Invoke 前的断点右键设置条件 `partId == "实际零件ID"`，命中后再开启 C++ 断点并继续。原生 `detect` 参数没有 `partId`，不要把它写成 C++ 条件。并行度为 1 也不保证零件按指定顺序出现。

| 位置 | 建议观察 | 解释 |
|---|---|---|
| C# 调用前 | `partId`、`core`、`snapshot`、输入 Mat 尺寸 | 确认目标件、搜索上下文和参数快照 |
| C++ 入口 | `alpha.rows/cols`、`cis.rows/cols`、`config.core_x/core_y/core_width/core_height` | 核心坐标相对搜索图，不是整张 TIFF 全局坐标 |
| 初始化后 | `core`、`scale`、`config.layout_dpi`、`config.enable_alignment` | 普通尺度可能受最小宽度修正，不在变量初始化前读它 |
| `register_patch(...)` 返回后 | `alignment.applied`、`alignment.info`、`alignment.transform` | 是否真正采用局部矩阵，不能只看开关；关闭局部配准仍进入 detect |
| 返回前 | `result.summary`、`result.alignment`、`result.defects` | 核对三类计数和配准状态；图像按请求生成 |

输入像素由 C# 同步借用，保持只读；不要在监视窗口改阈值、矩阵、Mat 指针或调用带副作用的函数来“试到通过”。单步暂停影响计时，不能作为性能数据。

#### 断点不命中时按顺序排查

| 表现 | 操作 |
|---|---|
| `MSB8036`、缺 SDK | 安装生成工程指定的 Windows SDK 后重建，不能拿旧 DLL 当新构建成功 |
| 找不到 Debug DLL/PDB | 先完成第二步；只有 Release 或 `-PrepareOnly` 成功不够 |
| 模块中没有 CISVisionCore.dll | 确认 PID 和本机引擎，开始离线回放；仍没有模块则从 C# P/Invoke 入口检查实际调用 |
| 模块路径是旧 bin/其他目录 | 关闭对应程序，从独立输出 EXE 重启并附加；复制磁盘 DLL 不会替换进程已加载模块 |
| PDB 未加载/不匹配 | 查看符号加载信息，复制与 DLL 同次构建的链接器 PDB；不用 C# PDB 或 `CISVisionCore.dir` 下的编译器 PDB 代替 |
| 源文件与原始版本不同 | 保存源码，停止调试，重编 C++、重建应用、复制 PDB、重启附加；保留源码匹配检查 |
| C# 命中但 C++ 仍为空心 | 检查是否只附加托管引擎、是否用了 Release DLL、符号是否加载。跨 P/Invoke 的 F11 不一定直接停在内部函数，可用行断点或函数断点 `cis::patch::detect` |
| 符号正常但始终不进入 detect | 查日志：未拼接、排版缺失/关联失败、全局对准失败、无 Alpha、全为 QRCode 区域、空 ROI 或作业取消；Completed 且零结果也不证明进入了检测 |
| 能进入 detect，但 register_patch 不命中 | 检查 `config.enable_alignment`，该开关不控制 detect 本身，不为断点擅自改变正式配置 |
| 跳行、变量被优化 | 确认原生 Debug DLL/PDB；C# 工具栏 Debug 标签不能证明 C++ 配置。F11 跳过自有代码时再查 VS“仅我的代码”等单步选项 |

#### 调试完成与下一次修改

本节使用独立目录，现场 bin 无需替换。每次改 cpp：停止进程 → 增量构建原生 Debug → 按第三步重建独立应用并复制 PDB → 重启附加 → 查模块。仅保存文件不会更新内存代码。

退出时停止采集并关闭调试程序，恢复调试副本临时改过的并行度。正常运行/测性能仍用 Release 原生库。若自行把 Debug 部署进默认 bin，停止程序后用 `dotnet build CIS_WebInspector.sln --no-restore -c Debug -p:Platform=x64 -p:VisionNativeConfiguration=Release` 恢复该目录，核对 DLL 与 `core-build/Release` 哈希一致；没有 Release 产物时先按第 1 节构建 Release。

VS 操作依据：[微软混合调试说明](https://learn.microsoft.com/en-us/visualstudio/debugger/how-to-debug-in-mixed-mode)、[附加进程说明](https://learn.microsoft.com/en-us/visualstudio/debugger/attach-to-running-processes-with-the-visual-studio-debugger)、[DLL/PDB 匹配规则](https://learn.microsoft.com/en-us/visualstudio/debugger/specify-symbol-dot-pdb-and-source-files-in-the-visual-studio-debugger)。本项目路径、默认值及调用链以源码核查为准；本次未实际完成 VS 命中断点，验证范围见维护记录。

### 裁框边界干扰回归

`Tools/RegistrationChecks` 是独立开发验证入口，不进入生产 UI。构建后执行：

```powershell
cmake -S Tools/RegistrationChecks -B obj/RegistrationChecks -A x64 -DOpenCV_DIR="$root/obj/VisionNative/opencv-build"
cmake --build obj/RegistrationChecks --config Release --parallel 2
& '.\obj\RegistrationChecks\Release\RegistrationChecks.exe' --boundary-checks
& '.\obj\RegistrationChecks\Release\StabilityChecks.exe'
```

8 项合成检查覆盖四边分别/同时进入碎片、完整小散点（含恰好接触边界）保留、大面积主体穿边不删除，并检查输入只读和被配准忽略的像素仍能参与内部缺陷检测。它们不替代真实图库验收。

`StabilityChecks` 的 15 项检查覆盖稀疏不同位置、复制方向不改变复核、内点顺序、单点无法伪装充分证据、真实不稳定仍拒绝、错周期仍拒绝、孔洞内散点和输入只读，以及三个独立已知变换（平移、小旋转/缩放、轻微非等比/剪切）。三个变换比较的是独立真值，不以自身内点充当精度真值；它们不代表真实生产缺陷精度。另外四项锁定轻微剪切可接受、过量剪切/缩放和镜像拒绝。该工具直接编译正式 `patch_alignment.cpp` 与 `patch_region.cpp`，不向 C ABI 增加测试函数。

真实图库可用 `PatchRegression --frames <图库> --registration-context --export-inputs --export-only --origin-y 58 --output <名称>` 导出全局对准后的原始输入；单件加 `--local-probe-part <PartId>`。导出的 `cores.json`、`thresholds.json` 必须与图像一起使用，不能把搜索外圈当成检测核心。用 `--raw-inputs <inputs目录> --benchmark-batch` 可核对 2 次预热和 10 次正式重复，`--parallelism 1` 可做串行对照；这些覆盖仅发生于验证进程，不回写现场配置。

### 固定真实原图上的裁框一致性

在上述导出命令中增加 `--export-frame <目录>`，可保存 `frame_alpha.png` 和 `frame_raw.png`（同一次全局对准、翻转后的实际输入），不需要另外加载独立 PNG 模板。为该目录准备 `sweep.json`：`dpi/alpha_threshold/cis_threshold/padding` 与实际配置一致，`cases` 中逐项指定 `name/core/target/dx/dy`；矩形使用 `x/y/width/height`，偏移用原像素，连续 Y 可改用 `dy_min/dy_max`。`target` 必须人工核对为完整目标包围框，不是算法的精度真值。

```powershell
& '.\obj\RegistrationChecks\Release\RegistrationChecks.exe' --roi-sweep '<整图与sweep.json目录>' '<输出目录>'
```

工具只移动裁框并从同一整图读取真实上下文，不平移/重采样原图。检查每个目标完整、基准确实应用了局部矩阵，再比较状态、模型、匹配/内点和原图九个固定探针的矩阵输出；任一探针差 ≥1e-6 原像素记失败，结果写入 `crop-sweep.tsv`。不能以全部拒绝获得通过，也不能把矩阵一致当作真实对准更准确。固定逻辑尺寸/原始像素的扰动才属于此项测试；曝光变化、不同膜片与大面积邻图另做鲁棒性测试。

性能测试必须单独串行执行改前/改后批次，不能与 C++ 编译、裁框扫描等重负载并行计时。候选 DLL 可只复制到验证工具目录，应用构建可加 `-p:OutputPath=obj/RegistrationCandidateBuild/Debug/` 保留现用 bin；正式部署前核对 DLL 哈希及精度、缺陷保留、重复性和耗时。具体版本的部署状态见维护记录，不能根据 cpp 已保存推断应用正在使用新算法。

`--benchmark-batch --cold-cache` 每批重建模板缓存，符合当前正式流水线缓存的生命周期；不加 `--cold-cache` 则跨批复用模板，只用于热缓存与重复性对照，不能当成实际整批节拍。两种测试均为已完成全局对准后的真实 ROI 批次，不含二维码、拼接、全局对准和图片保存。用 `--parallelism 1/4/8` 分别运行，并比较 `batch-performance.json` 中去除耗时后的 `Results`。

## 4. 常见故障定位

| 表现 | 先确认 |
|---|---|
| 找不到 CISVisionCore.dll | 是否先构建原生、C# 是否复制到正在启动的目录 |
| BadImageFormat / EntryPointNotFound | x64 是否一致，是否混入旧版 ABI |
| 没有白墨/缺陷图片 | 两个功能开关、SaveCroppedImages、输出路径和作业状态 |
| Completed 但结果数为零 | Alpha 是否存在、ROI 是否为空、是否全为 QRCode 辅助区域 |
| 调参数没有作用 | 改的是否实际运行目录配置、是否仍在使用旧会话/作业快照 |
| 更高并行度反而慢 | 内存带宽、图像编码、磁盘、原生算子并行叠加，而非只看 CPU 核数 |
| 缺陷面积与框面积不同 | 正常：面积来自真实连通域/断口掩膜，框包含背景 |
| SDK 与正式程序 QR 不同 | 核心是否同版本、CIS ROI/保护带/极性是否不同；静态例程必须重新链接 |

## 5. 安全修改步骤

新增配置先修改 AppConfig、设置 VM/XAML、快照传递、P/Invoke 映射和 C ABI；改变 ABI 字段需同步版本/size 检查和原生侧，不能只改其中一端。已有单位迁移必须保持兼容。

修改算法：固定正负样本 → 保存原输出 → 一次改一个因素 → 对比最终缺陷/坐标/图像 → 再测热机耗时和内存。性能比较需同并行度、同保存策略并分开首次加载，不把迁移前后测试中偶然更快的单次耗时作为本轮结构拆分收益。

修改职责/注释：优先保持表达式、遍历顺序、插值、参数、锁、取消/异常边界不变；使用现有回归证明等价。历史 Legacy 不随当前实现一起修改，否则对照失去意义。

## 在线相机信号与采集异常告警（2026-10-28）

正式入口：`CisCameraEngine.Connection.cs` 注册 `AriEvent_CameraStatusChanged`、`AriEvent_PendingGrabFinished`，并在采集期间每 250ms 读取 `AriProp_CameraStatus`。SDK 回调只记录原子状态；状态轮询、启动/停止/关闭及设置参数由设备锁串行，SDK 回调不获取该锁或直接停止设备。

- CLK1/2/3（位掩码 0x07）全部消失持续至少 1 秒，或状态读取连续失败至少 1 秒，触发“相机信号/采集异常”。任一时钟存在即清空失钟计时；读取恢复也清空读取失败计时。单次 SDK 调用抛异常或异步采集失败通知直接告警，不等待失钟确认。
- 不以“无新帧”或 Line/Frame 位消失判定掉线。因此编码器停转、产线静止本身不会触发无帧超时；但必须实测该相机在静止时是否仍输出至少一路有效时钟。如果相机设计为连时钟也门控，当前失钟判据可能误报，应先向厂家确认信号语义，不擅自更改检测算法。
- 每个加载会话只锁存一次故障；禁止继续交付新帧，后台立即写日志，UI 线程丢弃排队帧、请求取消当前检测作业、停止 SDK 采集并弹窗。正在执行的单次原生检测只在现有取消检查点退出，不是强制中断。
- 故障后即使恢复信号也不会自动恢复采集，需检查供电/线缆/板卡并重新加载相机配置。正常停止先禁用监测；离线数据源不接入此告警。切换来源或关闭窗口后，旧会话排队的告警不会操作新来源。
- `startGrab()` 或回调注册失败不再静默忽略。启动失败显示独立错误弹窗并写运行日志；初始化注册失败仍走既有初始化错误日志。

日志位置为当前运行目录的 `日志/SysRunLog_yyyyMMdd.txt`。运行故障检索 `[CameraConnection][ERROR]`，包含原因、状态读取成功与否、CameraStatus 十六进制值、最近状态事件值和最近 SDK 调用错误码/文字；最近错误码不等于异步事件自带错误码（该事件只提供成功/失败标记）。异常后 SDK 停止失败另写一条日志。

### 现场确认顺序

1. 正常加载、开始采集，检查正常产线与编码器静止各一段时间均不误报。
2. 在设备允许的操作条件下测试相机断电/信号中断：确认只弹一次、日志写入、采集状态停止，且当前作业取消；恢复后直接点开始应要求重新加载配置。
3. 恢复设备并重新加载，确认可重新采集；再次故障应产生新的一次告警。
4. 正常停止、关闭窗口、重新加载相机及切换离线图库，确认没有来自旧会话的误弹窗或停止新来源。
5. 启动时相机未供电、SDK 启动返回失败、SDK 状态读取失败，也分别核对弹窗/日志。不要用拔 PCIe 卡等操作替代按厂家要求进行的断连测试。

无硬件检查入口见 `Tools/CameraConnectionChecks/README.md`。本轮只验证判断逻辑及应用编译；尚未实测断电、驱动异常或弹窗。约 1 秒为连续异常确认窗口，不是端到端报警时延保证；SDK 调用阻塞或 UI 忙碌会推迟通知。仅依靠 SDK 可观测信号不能区分断电、线缆和采集卡问题，也不能发现“时钟仍正常但图像内容异常”的所有故障。
